# 永劫銀行 — 銀行システム サンプルパッケージ

預金（普通・貯蓄・当座・定期・外貨・通知）、融資（住宅ローン・事業融資・カードローン・当座貸越・シンジケートローン）、為替（振込・振替・口座振替・他行宛振込／全銀・海外送金）と、AML・リスク管理・顧客管理（CRM）を備えた銀行業務のサンプルです（架空データ・**本番利用不可**）。

| 層 | 技術 |
|---|---|
| フロントエンド | Next.js 15 (App Router) / React 19 / TypeScript 5 |
| アプリケーションサーバー | **IBM WebSphere Application Server Liberty**（Java 8, Servlet 4.0 / javax） |
| API | Apache Struts 2.6 系（6.13.0）+ struts2-json-plugin、JDBC |
| ビルド | **Gradle 8.14.3**（Wrapper 同梱、Java 8 向けにコンパイル） |
| データベース | **Oracle Database 23ai Free**（gvenzl/oracle-free、PDB `FREEPDB1`、スキーマ `BANK`） |
| 実行環境 | Docker Compose（oracle / liberty ×2 / frontend ×2 / lb（nginx）/ kong / mule / auth / redis。監視は profile `observability`） |

```text
ブラウザ ──▶ lb (nginx :3000) ──▶ frontend ×2 (Next.js)
                                    │  /api/bank/*  を同一オリジンでプロキシ（CORS 不要）
                                    ▼
             kong (:8000, Host: kong) ──▶ liberty ×2 (WebSphere Liberty, /bank/api/*)
                                    │  Liberty は Kong が付ける共有シークレットのない要求を拒否（ゲートウェイ迂回の防止）
                                    │  Struts 2 Action → Service → JDBC（JNDI DataSource jdbc/bankDS）
                                    │  ログインセッションも Oracle に保存（どのインスタンスでも継続）
                                    ▼
                                 oracle (Oracle 23ai Free :1521 / FREEPDB1)
```

## 起動

前提: Docker Desktop。初回はイメージ取得と Oracle の DB 作成に数分かかります。

```bash
cp .env.example .env    # パスワードを変更（.env はコミットしない）
```

```bash
docker compose up -d --build
```

```bash
docker compose ps
```

すべて `healthy` になったら http://localhost:3000 を開きます。

Windows の Docker Desktop で `use docker --context=desktop-linux buildx ...` エラーになる場合は、`COMPOSE_BAKE=false DOCKER_CONTEXT=desktop-linux docker compose up -d --build` を使ってください。

```bash
docker compose down
```


## ログインとデモユーザー

すべての画面・API はログインが必要です（`/health` を除く）。デモユーザーのパスワードはすべて `BankDemo#2026` です（架空データ用。実環境では使用しないでください）。

| 利用者ID | 役割 | できること |
|---|---|---|
| `yamada` / `sato` / `suzuki` / `takahashi` | お客さま（CU0001〜CU0004） | 本人名義の口座の照会・取引履歴・利息見込み、振込（本人口座から）・振替 |
| `teller1` | 窓口担当 | 全口座の照会、入金・出金、振込・振替、口座開設の申込受付、口座開設、顧客ログインの発行 |
| `supervisor1` / `supervisor2` | 役席 | 窓口担当の操作 + 本人確認の判定、解約、休眠解除、利息決算、休眠管理、夜間バッチ、監査ログ |

- 窓口で発行した顧客ログインは初期パスワード（画面に一度だけ表示）で、初回ログイン時に変更が必要です。
- パスワードは PBKDF2-HMAC-SHA256（12 万回・ソルト付き）で保存。10〜64 文字・英字と数字を含むこと。
- 5 回続けて失敗すると 15 分ロック。ID の有無やロック理由以外の失敗理由は区別して返しません。
- セッションは HttpOnly・SameSite=Lax の Cookie（`BANKSESSION`）、15 分無操作でタイムアウト、ログイン時にセッション ID を再発行（セッション固定化対策）。
- お客さまが他人の口座・顧客情報を指定した場合は「見つかりません」（存在を推測させない）。

```bash
curl -s -c cookie.txt -X POST http://127.0.0.1:3000/api/bank/login -H "Content-Type: application/json" -H "X-Requested-With: XMLHttpRequest" -d "{\"userId\":\"teller1\",\"password\":\"BankDemo#2026\"}"
```

```bash
curl -s -b cookie.txt http://127.0.0.1:3000/api/bank/accounts
```

```bash
curl -s -b cookie.txt -X POST http://127.0.0.1:3000/api/bank/transfer -H "Content-Type: application/json" -H "X-Requested-With: XMLHttpRequest" -d "{\"fromAccountNo\":\"1000001\",\"toAccountNo\":\"1000003\",\"amount\":\"5000\",\"memo\":\"test\",\"idempotencyKey\":\"0f8fad5b-d9cb-469f-a165-70867728950e\"}"
```

Windows でスクリプトや curl から呼ぶ場合は `localhost` ではなく `127.0.0.1` を使ってください。ポートは IPv4 ループバックにのみ公開しているため、`localhost` だと先に `::1` への接続を試みて毎回約 200 ms 待たされます（ブラウザーは影響を受けません）。

## 性能上の工夫

| 層 | 内容 |
|---|---|
| JDBC | 明細取得は `setFetchSize(50)`（Oracle 既定のプリフェッチ 10 行では 50 件に 5 往復以上かかる）。口座一覧も同様にまとめて取得 |
| JDBC | 口座詳細（口座 + 明細）は 1 接続で取得し、プールからの取得・返却を 1 回に削減 |
| JDBC | 振込の残高更新 2 件・明細登録 2 件を JDBC バッチで送信（行ロック保持中の DB 往復 4 → 2）。ロック順序は従来どおり口座番号順 |
| Liberty | `statementCacheSize=30`（全 SQL を解析済みで再利用）、`queryTimeout=30s`（ロック待ち等で接続を抱え込まない）、`minPoolSize=5`、DB 再起動時は `purgePolicy=EntirePool` で古い接続を一括破棄、`oracle.net.CONNECT_TIMEOUT=5000` |
| フロント | `lib/query.ts` の stale-while-revalidate キャッシュ（メモリのみ）。画面遷移時は直前のデータを即表示して裏で再取得、同一リクエストは 1 本に集約、口座リンクのホバー／フォーカスで詳細を先読み、タブ復帰時に再取得 |
| フロント | 入金・出金・振込の後は（成功・失敗にかかわらず）関係口座のキャッシュを無効化し、表示中の画面は自動で最新化 |
| 融資 | 返済予定表の返済日（休業日なら翌営業日）は、期間分の休日を 1 回の照会で読み込んで判定（`BusinessCalendar.Holidays`）。420 回の予定表で 420 回あった休日の照会が 1 回に（返済シミュレーション・融資実行・条件変更） |
| 情報系 | 日次の取込みは、前日のスナップショットがあれば「前日の残高・融資残高・最終取引日 + その日の明細だけ」で作る（差分取込み）。明細の総数に関係なく 1 日分の明細量で済む。前日がない日（初回・期間取込みの初日）だけ全履歴から作り直す。差分と作り直しの結果が一致することをテストで確認 |
| DB | 取引日時の索引 `account_transaction (created_at)`・`loan_transaction (created_at)`（10_dw_performance.sql）。1 日分・期間の明細（情報系の取込み・90 日の取引回数・取引集計表）を全件走査せずに取得 |

## 業務ルールと整合性

### 口座開設・本人確認（KYC）

- 申込 → 本人確認 → 口座開設の順。本人確認が「確認済」の顧客だけが口座を開設できます（謝絶された申込者は再申込可）。
- 本人確認書類は運転免許証・マイナンバーカード・パスポート・在留カード。**番号は保存せず下 4 桁のみ**記録します。
- 18 歳以上のみ受付（未成年は親権者同意の手続きが必要なため対象外）。カナ氏名・生年月日が同じ顧客がいれば重複申込として受け付けません（名寄せ）。
- 同じ種別（普通・貯蓄）の口座は 1 顧客 1 口座まで。開設は顧客行をロックして判定するため、同時に申し込んでも重複しません。

### 利息・税金

- 利息 = Σ（日々の最終残高 × その日の年利%）÷ 100 ÷ 365、1 円未満切捨て。うるう年も 365 日で計算します。金利は `interest_rate` 表（種別・適用開始日ごと、初期値 普通 0.20%／貯蓄 0.25%）。
- 計算期間は「前回決算期間の翌日（初回は開設日）〜決算日の前日」。決算は `interest_settlement` に記録し、同じ期間を二重に決算しません。
- 税（個人・源泉分離課税）: 国税 15.315%（所得税 15% + 復興特別所得税 0.315%）と地方税 5% を**それぞれ** 1 円未満切捨て。明細には利息（税引前）と源泉税を分けて記帳します。
- 法人・非課税制度（マル優等）は対象外です。

### 口座解約・休眠預金

- 解約: 1 トランザクションで「解約日前日までの利息決算 → 全残高の払戻し（本人名義の口座へ入金、または現金）→ CLOSED」。凍結・休眠口座は解約前に解除が必要です。
- 最終異動日: お客さまによる入金・出金・振込の最終日時。**利息の入金は異動に含めません**。
- 休眠預金等活用法を簡略化したルール: 最終異動から 9 年・残高 1 万円以上で休眠前の通知を記録し、10 年経過かつ「残高 1 万円未満」または「通知から 1 か月経過」で休眠（DORMANT）にします。休眠口座は取引できず、本人確認済みの顧客の申出で解除します。通知後に取引があれば通知はリセットされます。
- 休眠化・通知の UPDATE は条件（状態・最終異動日）を再確認するため、処理中に取引のあった口座は対象から外れます。
- 実運用では、休眠預金の預金保険機構への移管、通知文書の送付、公告などの手続きが別途必要です。

### 権限・監査・上限

- 役割（お客さま／窓口担当／役席）ごとに API を制限（`struts.xml` の `apiGuardRead.roles` / `apiGuardWrite.roles`。未設定の API はログイン必須で、公開にはならない）。
- 職務分離: 本人確認の判定は役席のみ、かつ申込を受け付けた本人は判定できません。解約・休眠解除・利息決算・休眠化も役席のみ。
- 監査ログ: すべての更新操作、ログイン成功／失敗、権限エラー、顧客情報の閲覧を、業務処理とは別トランザクションで記録（業務エラーで取り消された操作も残る）。各行は直前行のハッシュを含む SHA-256 でつながり、`/audit-verify` で書き換え・削除を検出します。
- 日次上限: 1 口座あたり 1 日の出金・振込（出）合計 20,000,000 円（口座行ロック中に集計するため同時実行でも正確）。1 回あたりの上限 10,000,000 円と併用。

### 夜間バッチ

- Liberty 内で 10 分ごとに確認し、毎日 01:00 以降に実行（`BANK_JOBS_ENABLED=true`、compose の既定は有効）。

### 情報系（DWH・経営管理・顧客分析・帳票）

勘定系（口座・明細・融資）とは別に、業務日ごとの**日次スナップショット**を情報系の表（`08_information.sql`）に持ちます。
経営ダッシュボード・顧客分析・帳票はこの表だけを読むので、勘定系の更新処理（行ロック）と競合しません。

| 表 | 内容 |
|---|---|
| `dw_account_daily` | 口座ごとのその日の終わりの残高（円換算付き）・状態 |
| `dw_loan_daily` | 融資ごとのその日の終わりの残高・格付・債務者区分 |
| `dw_daily_kpi` | 銀行全体の指標：預金（流動性・定期・外貨）、貸出金、不良債権、顧客数・口座数、新規・解約、取引件数、入出金額、貸出金利息・手数料・預金利息 |
| `dw_customer_daily` | 顧客ごとの預かり資産・借入・保有商品数・最終取引日・90 日の取引回数・RFM スコア・セグメント |

- **ETL**: 夜間バッチ `DW_LOAD`（ほかのジョブの後）が前日分を取り込みます。DWH が空なら直近 30 日分をまとめて取り込みます。
  経営ダッシュボードの「情報系データの取込」（役席）から、過去日の取込みややり直しもできます（1 回 92 日まで）。
- **過去日の再現**: 口座残高は「その日までの最後の明細の取引後残高」、融資残高は「最後の融資取引の残高」から作ります。
  元帳検証で残高と明細の一致が保証されているので、過去日の残高も正確に再現できます。
- **冪等**: 1 日分を 1 トランザクションで「削除 → 挿入」するため、同じ日を何度取り込んでも結果は同じです。
- **RFM とセグメント**: R＝最終取引からの日数（30 日以内 5〜365 日超 1）、F＝90 日の取引回数（20 回以上 5〜0 回 1）、
  M＝預かり資産（1,000 万円以上 5〜10 万円未満 1）。優良（R≥4・M≥4）／成長（R≥4）／休眠リスク（R≤2・M≥3）／離反（R≤2）／一般。
- **クロスセル**: 預かり資産 300 万円以上で定期なし → 定期預金、500 万円以上で外貨なし → 外貨預金、個人で貯蓄なし → 貯蓄預金、
  法人で当座なし → 当座預金、取引があり口座振替の契約なし → 口座振替。
- **離反リスク**: 資産はあるが取引が途絶えている顧客（休眠リスク）と、30 日前より預かり資産が 30% 以上減った顧客。
- **簡略化**: 外貨の円換算は取込時点の仲値、債務者区分・格付・凍結は取込時点の値を使います（相場や区分の履歴は持たない）。
  期間損益は円口座の取引から集計した概算で、人件費・物件費・税は含みません。

### 預金商品

| 種類 | 主なルール |
|---|---|
| 普通・貯蓄 | 入出金自由。利息は日々の最終残高で計算し年 2 回決算 |
| 当座 | 法人のみ・無利息。当座貸越契約で極度額までマイナス残高にでき、貸越残高に貸越利息（決算時に徴収） |
| 定期 | 3 か月〜5 年・10,000 円以上。作成時の金利で固定（単利）。満期は「元利金を資金口座へ」か「元利継続」（夜間バッチ）。中途解約は普通預金金利で再計算 |
| 外貨（USD/EUR） | 残高はセント単位。円口座との両替のみ（TTS で買い 1 円未満切上げ、TTB で売り 1 円未満切捨て）。利息は通貨ごとの金利 |
| 通知 | 50,000 円以上・据置 7 日。払出しは 2 日前まで（休業日は翌営業日）の通知が必要で、通知した金額以内で払い出せる |

定期・外貨口座では現金の入出金・振込はできません（専用の手続き）。解約時は外貨残高 0・当座貸越の返済・融資の返済用口座でないことが必要です。

### 融資

- 流れ: 申込（窓口またはオンライン）→ 与信審査（スコアリング）→ 承認／謝絶（役席・受付者とは別の人）→ 担保・保証の設定 → 契約（返済用口座・返済日）→ 融資実行 → 返済。
- スコア: 返済比率（DTI）40 / 担保掛目（LTV）25 / 年収 15 / 取引年数 10 / 延滞 −30 の 100 点満点 → 格付 A〜E → 金利 = 商品の基準金利 + 格付の上乗せ。返済比率 40% 超・総量規制（個人の無担保は年収の 1/3 まで）・完済時 80 歳超は謝絶推奨（承認するなら理由が必要）。
- 返済: 元利均等（返済額一定・1 円未満切上げ）／元金均等。月利息 = 残高 × 年利 ÷ 12（1 円未満切捨て）。返済日が休業日なら翌営業日。充当順は遅延損害金（年 14.6%）→ 利息 → 元金。繰上返済は返済額軽減型。
- カードローン（リボルビング）: 極度額の範囲で借入、日割利息を夜間に計上、返済は利息 → 元金。当座貸越: 当座預金の極度額として設定。シンジケートローン: 参加行の分担額の合計 = 組成総額、当行分 = 貸出額。
- 夜間バッチ: 約定返済の口座引落し（残高の範囲で充当）、延滞日数から債務者区分（正常先 / 要注意先 1〜89 日 / 要管理先 90 日〜 / 破綻懸念先 180 日〜 / 実質破綻先 365 日〜）を更新。延滞は督促記録を残し、破綻懸念先以下は役席が償却できます。

### 融資の管理（貸倒引当金・担保の再評価・条件変更・返済シミュレーション）

- **貸倒引当金**（簡略化した自己査定）: 正常先 0.5%・要注意先 3%・要管理先 15% は貸出残高に、破綻懸念先 70%・実質破綻先／破綻先 100% は
  **非保全額**（残高 − 保全額）に掛けます。保全額 = 担保の評価額 × 掛目（不動産 70%・預金 100%・有価証券 60%・保証会社 100%・個人保証 50%）、
  残高が上限。夜間バッチ（約定返済・延滞判定の後）と業務処理画面から見直し、前回との差額を積み増し・取り崩して履歴（`loan_provision`）に残します。
  同じ日に何度実行しても、必要額が変わらなければ何も記帳しません。完済で全額戻入、償却では引当を取り崩し、不足分を損失として摘要に記録します。
- **担保の再評価**（役席）: 評価額を更新して履歴（`collateral_revaluation`）を残し、実行済みの融資ならその場で引当を見直します。
  審査前の再評価は与信審査の担保掛目（LTV）にも反映されます。
- **条件変更**（役席・証書貸付のみ）: 残りの元金を新しい回数（最大 420 回）と、据え置きまたは引き下げた金利で返済し直します。
  未払いの回は取り消し（一部入金済みの額は残す）、延滞中の未払利息は新しい 1 回目に上乗せして延滞を解消します。
  条件を緩和した債権（貸出条件緩和債権）は**要管理先以下**として扱い、夜間の延滞判定でもそれより良い区分にしません（卒業の判定は対象外）。
- **返済シミュレーション**: DB に書き込まずに返済予定表を作ります（返済日が休業日なら翌営業日）。お客さまも利用できます。
- 役席が破綻先と認定した区分は、夜間の延滞判定で上書きしません。

### 為替

- 振込（当行あて）・振替（本人口座間）は `/transfer`。他行宛振込は手数料 330 円（3 万円未満）／440 円、15:00 以降・休業日は翌営業日扱い。全銀データ作成で総合振込フォーマット（ヘッダー・データ・トレーラー・エンド、各 120 バイト・半角カナ）を作り送信済みに、決済完了で決済済み。送信前は取消（手数料も返金）、送信後は組戻し（手数料は返金しない）。
- 被仕向（他行からの振込）は口座番号と受取人名（カナを正規化して照合）が一致すれば入金、不一致は保留して役席が入金か返却を判断。仕向銀行コード + 照会番号で一意にし、同じ振込データを再取込しても二重入金しません（結果は「重複」）。
- 口座振替の請求データは「契約 + 引落日」で一意。同じ請求ファイルの再取込は「重複（取込済み）」になります。
- 口座振替: 収納企業・お客さま番号ごとの契約、請求データの取込、引落日の処理（結果コード 0 振替済 / 1 資金不足 / 2 取引なし）。
- 海外送金: 円口座（TTS 換算）または同じ通貨の外貨預金から。手数料 4,000 円。受取人名を制裁リストと照合（語順・綴りの揺れを吸収する類似度 0.85 以上）、高リスク国も保留して役席が送金または謝絶（全額返金）。送金時は SWIFT MT103 形式の電文を作成。

### AML・リスク管理・CRM

- AML: 10 分ごとに新しい取引を検査（大口現金 200 万円以上・分割入金・短期間の入出金・海外送金の制裁リスト／高リスク国・国外送金等調書の対象）。アラートは未対応 → 調査中 → 問題なし／届出済（理由必須）。
- 信用リスク: EAD = 残高 + 未使用枠 × 50%、LGD = 担保カバー部分 10%・無担保部分 45%、PD = 格付の値を債務者区分で補正、EL = PD × LGD × EAD。流動性は預貸率と 30 日以内の定期満期、為替は外貨預金の売り持ちと円安 1% の影響。
- CRM: 顧客 360°（預かり資産の円換算と顧客区分、融資・申込、定期、口座振替、AML アラート）、接触履歴（訪問・電話・提案・苦情・メモ）。

### 共通

- 更新系は 1 トランザクション: **冪等キー登録 → 口座行ロック（`SELECT ... FOR UPDATE`）→ 残高検証 → 残高更新 → 明細登録 → コミット**。
- 振込は 2 口座を**口座番号順にロック**し、逆方向の同時振込でもデッドロックしません。
- 冪等キー（`OPERATION_REQUEST` 主キー）で二重送信・リトライによる二重計上を防止。業務エラー時はキーもロールバックされ、同じキーで再試行できます。
- 残高は `NUMBER(15,0)` + `CHECK (balance >= 0)`、明細は取引ごとに取引後残高を保持。
- 凍結・解約口座は取引不可。

## 信頼性・整合性・高可用性

### ACID トランザクション

- 1 操作 = 1 DB トランザクション（`Transactions.inTransaction`）。途中で失敗すれば口座残高・明細・冪等キー・関連表のすべてがロールバックされます。
- 一時的な DB エラー（接続断・フェイルオーバー、デッドロック ORA-00060、直列化エラー ORA-08177 など）は**コミット前に限り**最大 3 回まで自動で再試行（50・200 ms 待機）。コミット中の障害は結果が不明なため再試行せず、エラーを返します（同じ冪等キーで再送すれば、実行済みなら前回の結果、未実行なら新たに処理）。
- 読取り一貫性は Oracle の READ COMMITTED（文レベルの読取り一貫性）、更新は行ロックで直列化します。

### 排他制御

- 残高を変えるすべての処理（入出金・振込・利息・解約・融資・口座振替・被仕向・両替など）が、更新前に口座行を `SELECT ... FOR UPDATE` でロックし、ロック後の残高で検証します。複数口座は口座番号順にロックしてデッドロックを防ぎます。
- 日次上限の集計も口座行ロック中に行うため、同時実行でも上限を超えません。
- 検証: 同じ口座への 20 件同時出金で残高を超える出金が 1 件も成立しないこと、双方向 80 件の並行振込で 2 口座の合計が保存されることをテスト・実環境で確認。

### 二重処理防止（冪等性）

- すべての更新 API は `idempotencyKey`（画面は操作ごとに UUID を自動付与）が必須。キーは `OPERATION_REQUEST` の主キーで、同じキーの同時送信も 1 件だけが実行されます。
- 実行済みのキーで再送されると、**前回の処理結果をそのまま返します**（応答に `"replayed": true`、監査ログの詳細は `REPLAYED`）。通信断で結果を受け取れなかった画面・ロードバランサーの再送でも、残高は 1 回分しか動きません。
- 同じキーで内容の違う依頼は `IDEMPOTENCY_KEY_REUSED`（422）、先の処理が実行中なら `REQUEST_IN_PROGRESS`（409）。
- 外部から届くファイルも二重取込を防止: 被仕向振込は「仕向銀行コード + 照会番号」、口座振替の請求は「契約 + 引落日」で一意。

### 高可用性

- `lb`（nginx）の背後に API（Liberty）2 台・画面（Next.js）2 台。停止・異常のインスタンスは自動で外され、接続エラー・タイムアウト・502/503/504 は**もう一方のインスタンスへ再送**されます（POST も再送。冪等キーにより二重実行にならない）。
- ログインセッションは Oracle（`BANK_HTTP_SESSIONS`、Liberty `sessionDatabase-1.0`）に保存するため、片方の停止・再起動・ローリング更新でもログアウトされません。
- ヘルスチェック: `/bank/api/health`（DB に接続できなければ 503 = ロードバランサーから外れる）、`/bank/api/live`（プロセスの生存。応答にインスタンス名）。
- 夜間バッチは各ジョブを `JOB_RUN` の主キーで取得するため、複数インスタンスでも 1 日 1 回。
- 台数は `.env` の `LIBERTY_REPLICAS` / `FRONTEND_REPLICAS`（3 台以上にする場合は `lb/nginx.conf` の `server` 行も追加）。
- 検証: 操作中に API インスタンスを 1 台停止しても約 450 件の要求がすべて成功、ログイン状態も継続。停止したインスタンスは再起動後に自動で復帰。画面インスタンスの停止でも要求は失敗しません。
- 範囲外: Oracle は 1 台（単一障害点）。本番では Data Guard（スタンバイ切替）や RAC、定期バックアップ（RMAN）と復旧手順が必要です。Liberty の接続プールは DB 再起動後に接続を作り直し、一時エラーは上記の再試行で吸収します。

### 監査証跡

- **操作履歴**: 監査ログ（誰が・いつ・どこから・何を・結果）。行ごとに SHA-256 のハッシュチェーンでつなぎ、`/audit-verify` で書換え・削除を検出。利用者 IP はロードバランサーが付ける `X-Forwarded-For` から記録します。
- **取引履歴**: 取引明細も口座ごとにハッシュチェーン（明細登録時、口座行のロック中に直前の明細のハッシュを含めて計算）。この機能より前の明細は最初の検証時にハッシュを付けます。
- **元帳の検証**（`/ledger-verify`、監査ログ画面の「元帳を検証」、夜間バッチ `LEDGER_CHECK`）: ハッシュチェーン、残高の連続性（直前残高 ± 金額 = 取引後残高）、口座残高と最新明細の一致、振込の出金・入金の対応。
- **取引の追跡**（`/ledger-trace`、行員の口座詳細画面「取引の追跡」）: 明細と、それを実行した操作（監査ログ）を冪等キーで結び付け、取引ごとに操作者・時刻・IP を表示。夜間バッチ等のシステム処理はその旨を表示します。

## 外部連携（Kong × MuleSoft）

画面の API は **Kong Gateway**（OSS 3.9・DB-less）を通って Liberty ×2 に届きます（流量制限・ヘルスチェック付きの負荷分散）。
他行の全銀データ・収納企業の請求データ・為替相場は、連携先が OAuth 2.0 のアクセストークン（`/oauth2/token`）で
`http://127.0.0.1:8088/integration/v1/*` を呼び、**MuleSoft**（Mule 4 の Process API。ローカルでは同じ API 契約の互換コンテナ。Kong とは mTLS）が
検証・変換して勘定系へ取り込みます。同じデータの再送は冪等キーで 1 回だけ処理され、実行履歴は Oracle に残ります。
役席は ADMIN →「外部連携」から送信できます（**二者承認**：作成した役席とは別の役席が承認したときだけ送信）。

初回は `bash integration/scripts/gen-secrets.sh >> .env` で秘密情報（OAuth の鍵とクライアントシークレット・mTLS の証明書・共有シークレットなど）を作り、
`MULE_CORE_PASSWORD` を加えて、`12`〜`14` の DB スクリプトの適用と `python integration/scripts/set_service_password.py` で連携用アカウントを有効化します。
強化の 12 項目（実行履歴の永続化・二重入金防止・職務分離・ゲートウェイ迂回防止・行員 ID の署名・OAuth/mTLS/Entra ID・CSRF・再処理・
分散流量制御・監査ログ保護・統合監視・構成管理）は [integration/docs/hardening.md](integration/docs/hardening.md)。
手順・設計（ADR・経路・セキュリティ・運用）は [integration/README.md](integration/README.md) を参照してください。

## セキュリティ設定（Struts 2）

`struts.xml`: devMode=false、Dynamic Method Invocation 無効、`action:`/`method:` プレフィックス無効、静的フィールドアクセス無効、`struts.parameters.requireAnnotations=true`（`@StrutsParameter` を付けた setter のみ値を受け付け）。Liberty は `X-Powered-By` を無効化、エラー時は詳細を返しません。
